# 08 · 真实网络打洞实测（PC 家宽 ↔ 手机 5G）

2026-10-16。从 netns 实验室走到真实网络：一端是家里 Wi-Fi 下的 PC，一端是走电信 5G 的手机（USB 调试，Wi-Fi 关闭），服务器 99-server 做 STUN 和对照测试。第 2、3 节做的时候安全组还没放行，所以会合由脚本代劳；第 4 节是放行之后用服务器补测的。

## 1. 三方情况

| | PC | 手机 | 服务器 |
|---|---|---|---|
| 设备 | CachyOS，家里 Wi-Fi | vivo V2238A，Android 14，电信 5G SA，Wi-Fi 关 | 阿里云 ECS |
| 本机地址 | 192.168.1.95（家用路由器后） | 100.106.143.213（运营商私网 100.64/10，即 CGNAT） | 内网 172.21.191.78，1:1 映射到 8.140.18.211 |
| 公网地址 | 110.228.186.81 | 106.9.69.144 | 8.140.18.211 |
| 全球 IPv6 | 无 | **有**（240e:…，电信） | 无 |
| 代理 | sing-box TUN，测试时绑定 wlan0 地址绕开 | 有 VPN，但只按应用分流，adb shell（uid 2000）不走 | — |
| 到服务器 ping | 24ms | 41ms | — |

手机上跑的是交叉编译的静态二进制（`GOOS=linux GOARCH=arm64 CGO_ENABLED=0`），通过 adb 推到 `/data/local/tmp`。adb shell 里没有 `/etc/resolv.conf`，所以工具只接受 IP，不做 DNS 解析。

## 2. 两端 NAT 的行为（`lab/natprobe`）

| 项目 | PC（家用路由器） | 手机（电信 CGNAT） | 怎么测的 |
|---|---|---|---|
| 映射 | **EIM**，且端口保持 | **EIM**，端口不保持 | 同一 socket 问 4 个不同 IP 的公共 STUN，映射都一样 |
| 端口分配 | 映射端口 = 本地端口；10 个里有 1 个冲突，退到了 1025 | 在一个端口块里随机：16 个样本全在 18684~18904 | 依次新开 socket 问同一个 STUN |
| 过滤（陌生 IP） | 进不来 | 进不来 | 一端只收不发，另一端往它的映射地址发 |
| 过滤（同 IP 换端口） | 进不来 | 进不来 | X 先向 Y 的 socket1 发包，再让 Y 的 socket2 往 X 发 |
| 结论 | **EIM + APDF（端口受限锥形，俗称 NAT3）** | **EIM + APDF（NAT3）** | |

过滤测试原本要靠服务器的"备用端口"做，这里改成让两个对端互为"另一个 IP"：PC 和手机的公网 IP 不同，各开两个 socket 又能得到"同 IP、不同端口"。**三方里任何两方都能给第三方当测试对象，单 IP 的服务器做不到的"换 IP 过滤测试"反而只能这样做。**

**CGNAT 的端口块**：连开 64 个 socket，映射端口全部落在两段里：18682~18924 和 1~437。说明运营商按"端口块"给每个用户分端口（RFC 7422 一类做法），一个块大约几百个端口，用完或者旧映射还没过期时再分一块。两个推论：
- 即使这类 CGNAT 是对称型的，要猜的也只是块里的几百个端口，不是整个 64K。生日攻击的成本因此降两个数量级。
- 一台手机短时间内开很多 socket（比如生日攻击开 256 个），会把自己的端口块用完、触发分配新块；块里还有其他 App 的映射，所以能用的比块大小少。

## 3. 打洞：不用会合服务器

会合服务器唯一的职责，是把双方的映射地址交给对方。`natprobe peer -file f` 每 100ms 读一次文件里的目标地址，于是"会合服务器"在脚本里就是这两行：

```bash
echo $手机映射 > /tmp/peer-pc.txt                        # 交给 PC
adb shell "echo $PC映射 > /data/local/tmp/peer.txt"      # 交给手机
```

两端都是 NAT3，按理论只要双方同时向对方的映射地址发包就能打通。实测：

- **成功率**：同时开始 30+ 次，全部打通；之前的单项测试也没有失败过。
- **直连 RTT**：p50 约 37~44ms，p95 55~130ms。走服务器中转的估计值是 24 + 41 ≈ 65ms，而且服务器出方向只有 3Mbps。
- **谁先发都没关系**：让一方先单独发 2 秒、另一方再开始，双方看到的对端来源地址都等于 STUN 映射，没有被换端口。也就是说，这两个 NAT 收到陌生包时都是直接丢掉、不留状态，不会出现 netns 实验室里 Linux NAT 的 conntrack 冲突（06 第 2 节）。**这一对网络用不上低 TTL 预热**，但换成其他路由器还是要测。
- **20ms 一个包时的丢包率**：约 0.5%（925 个丢 5 个左右）。

### 3.1 建连耗时与"触发检查"

双方几乎同时拿到对方地址，统计"从自己发第一个包到收到对方的确认"用了多久（各 10 次取平均，30 次全部成功）：

| 配置 | PC | 手机 |
|---|---|---|
| 每 200ms 发一个，无触发检查 | 250ms | 61ms |
| 每 200ms + 触发检查 | 139ms | 50ms |
| 每 20ms + 触发检查 | **88ms** | **47ms** |

PC 总是慢一些，原因是 PC 先拿到地址（本机写文件），手机要经过 adb 晚 50~100ms 才开始发。PC 的头几个包到达电信 CGNAT 时，手机还没为 PC 开洞，于是被丢掉。手机的包到达家用路由器时，PC 已经开过洞，直接进来。PC 回了 ACK，所以手机一个 RTT 就打通了。PC 这边却要等自己的**下一个**探测包：
- **触发检查**（ICE 的 triggered check）：一收到对方的第一个包就立刻回发一个探测，不等下一个周期。PC 平均从 250ms 降到 139ms。
- **探测间隔从 200ms 缩到 20ms**：剩下的等待时间也压缩掉了，降到 88ms，大约是"两端开始时刻之差 + 1 个 RTT"，已经接近下限。

对比一下：UU 远程（WebRTC ICE）12 秒打不通才回退中继。只要 NAT 类型合适，打洞本身是百毫秒级的事。用户感受到的连接慢，主要花在信令往返、候选收集、TLS/DTLS 握手和保守的超时上。

### 3.2 发包密度和 RTT（初步）

打通后两端按不同间隔互发 20 秒：

| 间隔 | RTT p50 | p95 | max |
|---|---|---|---|
| 20ms | 36ms | 55ms | 162~180ms |
| 200ms | 44~47ms | 119~127ms | 800~930ms |
| 1s | 38~44ms | 58~108ms | 74~158ms |

20ms 时最稳；200ms 时出现了接近 1 秒的尖峰，推测和手机基带的省电状态切换（DRX/RRC）有关。样本还少，结论要多跑几次再定。对远控的启发是：画面静止、包很稀疏的时候，第一个操作的延迟可能会突然变大。要不要在空闲时也维持一定的包频率（代价是耗电），值得专门测。

## 4. 用服务器补测的几项（安全组放行后）

安全组规则的授权对象一开始只填了家里的公网 IP，结果 PC 能连、手机连不上。在服务器网卡上抓包，看到手机发往 51820（WireGuard）的包能到，发往 3478 的到不了，由此定位到授权对象，改成 `0.0.0.0/0` 后恢复。**抓包能区分"运营商在路上丢了"还是"安全组挡了"。**

| 项目 | PC（家用路由器） | 手机（电信 CGNAT） |
|---|---|---|
| 过滤（服务器备用端口） | 端口受限 | 端口受限，与第 2 节一致 |
| 低 TTL 开洞 | **TTL ≥ 2** | **TTL ≥ 5**（CGNAT 在第 4 跳） |
| 到服务器的跳数 | 11 | 12 |
| 映射寿命（静默后外面还能进来） | **60~90 秒** | **2~3 分钟** |

- **低 TTL 预热的取值**：TTL 至少要让包"走出"本方 NAT，NAT 才会记下映射（这和 netns 实验室里 Linux 的表现一样：包要真正被转发出去才算数）。手机要 5 跳，PC 要 2 跳；到对方 NAT 大约 11 跳以上，中间有足够的余量。所以 punch 的 `-ttl` 不能写死成 2，要按本方实测值来，或者干脆取一个偏保守的值，比如 6。手机侧 k=15 和 k=64 各有一次没收到，这是单个回包丢了（服务端只发一次），不是规律。
- **保活间隔**：两端寿命的下限分别是 60 秒和 2 分钟，木桶取短板，所以**连接上至少每 30 秒要有一个包**。家用路由器反而比 CGNAT 更早忘掉映射。
- PC 那次中转测试的映射端口是 1025，而不是本地端口：家用路由器的端口保持偶尔会失败、退到 1025（第 2 节的端口分配测试里也出现过一次）。所以"PC 的映射端口 = 本地端口"只能当作猜测，不能当作事实。

### 4.1 直连 vs 经服务器中转

服务器上起一个最小的 UDP 中转（记住两个来源地址，互相转发），和直连交替各跑两轮，每轮 20 秒，每 20ms 一个包：

| 路径 | RTT min | p50 | p95 | 丢包 |
|---|---|---|---|---|
| 直连 | 28~31ms | 36~45ms | 52~56ms | ~0.3% |
| 中转（北京阿里云） | 38~46ms | 44~56ms | 58~67ms | ~0.4% |

服务器正好在两端中间（都在北方），中转只多出约 10ms。这时候直连的主要价值不在延迟，而在**带宽和成本**：中转受服务器出方向 3Mbps 的限制，直连没有这个上限，而且不花服务器的流量。如果两端在不同城市，或者中转节点选得不好，延迟差距会大得多。

另外：手机有 IPv6，PC 没有。如果家用路由器能打开 IPv6，PC↔手机就可以走 IPv6，完全没有 NAT 映射，只剩状态防火墙。这种情况双方同时发包就能打通，也不需要 STUN。
