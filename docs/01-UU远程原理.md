### 2. 架构还原

```
           ┌──────────── 信令/账号 (HTTPS + WSS?, protobuf) ────────────┐
           │  登录(JWT) · 设备列表 · 房间/分享码 · 交换 SDP/ICE 候选      │
           │  · 决定是否强制中继 · 下发 STUN/TURN 服务器列表              │
           └───────▲───────────────────────────────────────▲────────────┘
                   │                                       │
   被控端 GameViewerServer.exe                      控制端 GameViewer.exe / App
   采集(DXGI/WGC) → 硬件编码(NVENC/AMF/QSV)          硬件解码 → 渲染 → 输入回传
                   │                                       │
                   ├──────── ① P2P 直连 (UDP 打洞，~90%+) ──┤
                   │                                       │
                   └── ② TURN 中继 (UU 加速器节点，兜底) ────┘
```

一次连接的时序（标准 ICE 流程，UU 应基本相同）：

1. 双方各自向 STUN 服务器问"我在公网上是谁"→ 得到 **srflx 候选**（公网 IP:端口）；同时收集本机网卡地址（**host 候选**）、向 TURN 申请中继地址（**relay 候选**）。
2. 经信令服务器交换候选列表。
3. 双方**同时**向对方所有候选发 STUN Binding 连通性检查——这一步就是"打洞"：自己往外发的包在本方 NAT 上打开映射，对方的包就能进来。
4. 选出最优可用路径（host > srflx > relay）。12 秒左右还没通就用 relay。
5. DTLS 握手协商密钥 → SRTP 传音视频，SCTP DataChannel 传键鼠/剪贴板/文件。**[推断]** 也可能把 WebRTC 只当连通层，媒体用自研 "UDP+" 协议跑在同一条 5 元组上。

### 3. 为什么免费还能这么快——真正的原因

#### 3.1 经济学：P2P 让网易几乎不用付视频带宽
远控最贵的成本是**中转带宽**。国内 BGP 带宽按 Mbps 计价很贵；一路 4K144 流 30~100Mbps，如果都走服务器，免费根本撑不住。ToDesk/向日葵免费版慢，本质是**走中转时被限速**。
UU 的做法：
- 90%+ 会话打洞成功走 P2P → 视频流量走的是**你自家的上行带宽**，网易只承担信令（KB 级）。
- 剩下的走中继，用的是 **UU 加速器原有的节点网络**——基础设施已经存在、边际成本低。**[推断]** 加速器的高峰在晚上游戏时段，远程办公的高峰在白天，两者错峰。
- 因为不花钱，所以才敢把码率上限放到 500Mbps——**"像在家里"的画质主要来自"敢给码率"**。

#### 3.2 打洞成功率高：游戏加速器的老本行
加速器公司长期和国内各运营商的 NAT 行为、UDP QoS 打交道，积累了：
- 多台 STUN 探测 NAT 类型；对称 NAT 做**端口预测 / 端口喷洒**（见 02 §4）。
- 大量真实网络的端口分配规律统计（运营商、地区、光猫型号）。
- 节点就近选择、跨运营商（电信↔移动）的优化线路——中继也不慢。

#### 3.3 低延迟管线：云游戏/串流的技术路线
端到端延迟 = 采集 + 编码 + 网络单程 + 抖动缓冲 + 解码 + 显示

| 环节 | 典型做法 | 耗时 |
|---|---|---|
| 采集 | DXGI Desktop Duplication / Windows.Graphics.Capture，GPU 纹理零拷贝 | 1~3 ms |
| 编码 | NVENC/AMF/QSV 低延迟预设、无 B 帧、帧内刷新(intra-refresh)代替大 I 帧、切片 | 2~5 ms |
| 网络 | P2P 直连同城 5~20 ms；UDP、不等重传 | 变量 |
| 抗丢包 | NACK 选择重传 + FEC 前向纠错，按丢包率动态调整冗余 | — |
| 拥塞控制 | 类 GCC/BBR 的带宽估计，网络变差先降码率/分辨率而不是卡顿 | — |
| 抖动缓冲 | 尽量小（远控宁可偶尔花屏也不要累积延迟） | 0~10 ms |
| 解码显示 | 硬解 + 144Hz 下一帧仅 6.9 ms | 1 帧 |

用的是 **UDP + 自己控制重传**：TCP 的队头阻塞会让一个丢包卡住后面所有帧，这是基于 TCP 的远控"拖泥带水"的根本原因。

#### 3.4 商业动机 [推断]
导流到 UU 加速器 / 网易游戏生态、积累用户、以高级功能会员变现。免费不是做慈善，而是 P2P 架构让免费的边际成本接近 0。

### 4. 对自研的启示（一句话版）

> **P2P 打洞成功率决定了你的成本，UDP 传输 + 硬件编解码决定了你的体验，中继只是保底。**
