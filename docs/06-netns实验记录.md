## 1. 打洞成功矩阵（2026-10-16，`lab/punch`，未开喷洒）

默认配置：NAT 带路由器式防火墙，即 INPUT 链丢弃 WAN 上不请自来的包。

| A \ B | full | port | sym |
|---|---|---|---|
| **full** | ✅ | ✅ | ✅ |
| **port** | ✅ | ✅ | ❌ |
| **sym** | ✅ | ❌ | ❌ |

和 02 章的理论表一致：端口限制锥 ↔ 对称、对称 ↔ 对称，不做端口预测或生日攻击就打不通。

netem 校验：A 链路加 30ms、B 链路加 20ms±5ms 和 5% 丢包，测得 RTT p50 = 101.5ms，符合"每条链路双向各加一次"的预期（2×30 + 2×20 = 100ms）。

## 2. 发现：Linux NAT 的 conntrack 冲突会让端口限制锥之间也打不通

`--no-fw` 时（NAT 不丢弃 WAN 来的未请求包），**port ↔ port 也会失败**。抓包看到：

```
A 先发:  203.0.113.1:54608 → 203.0.113.2:48541   PUNCH A    （B 的映射端口是 48541）
B 后发:  203.0.113.2:35308 → 203.0.113.1:54608   PUNCH B    ← B 的出口端口变了
```

过程：
1. A 的 PUNCH 先到 natB。natB 没有防火墙，这个包被交给 natB 本机（回一个 ICMP 端口不可达），conntrack **确认**了一条 `A:54608 → natB:48541` 记录。
2. B 往 A 发包时，MASQUERADE 想用 48541 做源端口，但这个映射和第 1 步的记录冲突 → **换成 35308**。
3. A 的 NAT 是端口限制锥，只认 48541 回来的包 → 一直丢弃。
4. A 每 200ms 发一次 PUNCH，不断刷新那条旧记录，它永远不会过期 → 双方僵死。

为什么加了防火墙就没事：conntrack 记录要到包走完 INPUT/POSTROUTING 才会确认，在 INPUT 被丢掉的包不会留下记录。

对打洞引擎的启示（对应 05 章 2.3）：
- **低 TTL 预热**正好防的是这个：先用 TTL=3~5 的包在本方 NAT 上把映射建好，又不让包到达对方的 NAT，之后再正常发包。
- **同步开打**能缩小"对方的包先到"的时间窗口，但治不了根。
- 发现自己的出口端口变了以后（对方回包里带"我看到你的地址"），应该**换一个本地端口重新开始**，而不是对着一条死掉的映射一直发。
