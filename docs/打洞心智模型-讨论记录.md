## 打洞心智模型 · 讨论记录

目的：不背 NAT1~4 矩阵，而是建立能**自己推出矩阵**的心智模型。采用讨论 + 反问的方式，结论都尽量落到本仓库的代码上。
配套地图：`docs/arch/`（arch-map 生成，以打洞为主线）。建议阅读顺序：`20-flow-punch` → `30-netns-nat` → `21-flow-symmetric` → `22-flow-nat-profile`。

### 1. 骨架（2026-10-16）

1. **NAT 是一张状态表**，行为取决于表的 key 里有哪些字段：
   - 映射 key：分配公网端口时看不看目的地址 → EIM / EDM（对称型）
   - 过滤 key：入包核对哪些字段 → EIF（不核对）/ ADF（源 IP）/ APDF（源 IP + 端口）
2. **打洞 = 两个独立问题**：寻址（往对方哪个 IP:端口 发）和放行（包到对方 NAT 时有没有匹配的状态）。
   打不通时先问：是地址错了，还是被过滤了？
3. **时间维度**：出包要先在自己 NAT 上建好状态（低 TTL 预热）；状态会过期（保活）。

### 2. 已讨论的概念与结论

| 问题 | 结论 |
|---|---|
| STUN 服务器是什么 | 一面「镜子」：告诉你它看到的源 IP:端口（srflx）。必须站在 NAT **外面**（有 CGNAT 时看到最外层）。只解决寻址，且只在 EIM 时有效；不交换地址、不转发数据、问一次判断不了 NAT 类型。`punch` 的会合服务器顺手做了同样的事（`srv_see`） |
| socket 是什么 | 操作系统给程序的接口，在应用和内核传输层之间，不属于 TCP。UDP socket ≈ 绑定了本地 IP:端口的信箱，能和任何人收发。NAT 看不到 socket，只看包的源端口 |
| 为什么问 STUN 和打洞必须用同一个 socket | 换 socket = 换本地端口 = NAT 开新映射，告诉对端的地址不再指向你 |
| 换 socket 一定打不通吗 | 不一定：对端若是 EIF/ADF，你从新端口发的包仍能进去，对端从源地址学到真实端口（prflx）后回包即可。**换 socket 在对端看来等同于你在对称 NAT 后面**——这就是「ADF ↔ 对称能通、APDF ↔ 对称不能」的根源 |
| 打洞能代替翻墙跳点吗 | 不能。把问题拆成可达性 / 路径 / 审查三层，打洞只解决可达性；路线不变、目标网站不会跟你打洞，仍需墙外节点；打洞最多让 NAT 后的机器也能当跳点（Tor Snowflake 思路）。跨境速度看路径质量，UDP 国际出口 QoS 更重——UU 加速器靠专线中继，UU 远程才靠 P2P |
| 打洞一定需要中转服务器吗 | 区分三个角色：STUN（镜子）、信令（传话）、TURN（中转）。打洞**必须有传话渠道**（鸡生蛋问题），但形式不限——docs/08 用脚本 + adb 代替会合服务器已打通；**不需要中转**，TURN 是打不通时的兜底（如公司网络封 UDP，只能 TURN over TCP/443）。产品自建信令是为了及时、鉴权、反复交换，属于工程选择 |
| 它们在哪一层 | 都在应用层。STUN、TURN 是协议（TURN 是 STUN 的扩展）；信令是角色（WebRTC 故意不规定传输方式）；ICE 是流程。问题出在网络层 / 传输层（NAT 改写 IP 和端口），解法全在应用层 |
| QUIC 和 hy2 谁更好 | 不在同一层。QUIC 是传输层（UDP 上用代码重写了 TCP：编号、确认、重传、拥塞控制，外加多流、内置 TLS、连接迁移）；hy2 是 QUIC 之上的代理协议，只加了四件事：HTTP/3 认证、伪装（masquerade / Salamander 混淆）、TCP 走流 + UDP 走 DATAGRAM、Brutal 拥塞控制。p2pcp ≈ 去掉认证和伪装、再加上打洞的 hy2。「hy2 快」快在 Brutal 不让步（docs/09 第 6 节：设高了延迟到 1 秒），不是 QUIC 本身快（2026-10-22） |
| 重传是谁做的 | 不是网络自带的，是某一层自己选择要做的：IP、UDP 都不管；TCP 在内核里管；QUIC 在用户态库里管；应用也可以自己做（docs/07 的 own、KCP）。「可靠」是个功能，哪一层都能加 |
| 为什么不能把 tun 读出的 IP 包塞进一条可靠的 QUIC 流 | TCP over TCP：外层丢包后在补，里层的段其实没丢、只是在排队，里层却把**延迟误判成丢包**，于是重发（注定重复、白占带宽）并降速（同一次丢包被两层各罚一次），RTT 抖动又让它的超时越来越大 → meltdown。原则：**跨网那一段只留一层可靠**。forward / hy2 拆开 TCP 只走 QUIC；WireGuard 外层故意不重传，让里层看到真实丢包 |
| STUN/TURN 是文本协议吗 | 二进制。实测拆过一对包：请求 20 字节头（类型 / 长度 / 魔数 `2112A442` / 12 字节事务 ID），响应多一个 XOR-MAPPED-ADDRESS 属性。用二进制的理由：小而快；能和其他协议在**同一个端口**上区分（natprobe 服务端先 `isBindingRequest` 再当文本命令）；XOR 防路由器 ALG 改写。本仓库的 `REG`/`PEER`/`PUNCH`/`FILT` 是自家文本协议，因此公共 STUN 客户端问不了 punch 会合服务器（角色像 STUN，协议不是） |

| 为什么「ADF ↔ 对称」能通，「APDF ↔ 对称」不能（2026-11-09） | 寻址 + 放行两半。寻址：对称端经 STUN 拿到的端口（6000）只对 STUN 有效，往 A 发包时 NAT 换新端口（6123），A 知道的是错端口。放行：A 往 6000 发包，自家 NAT 登记的是 6000（A→B 方向在 B 的 NAT 被丢）；B 从 6123 打过来，ADF 只核 IP → 放行，A 从源地址学到 6123（prflx）回包，B 的 6123 本就是为 A:5000 开的 → 通；APDF 核端口 → 丢。一句话：**对称端的真实端口只有它主动发来的包能告诉你，ADF 放它进来，APDF 只认你事先登记的错端口**。前提：A 是 EIM、A 会学 prflx。实验室已补上 restricted（ADF）档并实测：restricted ↔ sym 5/5、port ↔ sym 0/5，A 从入包学到 B 的真实端口 10051（会合给的是 38907），见 docs/06 第 1.1 节 |
| APDF ↔ 对称怎么绕过（生日攻击，2026-11-09） | A 改不了自家 NAT 规则（CGNAT 不归你管），唯一杠杆是**往外发包会写表**：「允许 B 的所有端口」= 往 B 的每个端口都发一个包。「A 表里碰巧有 6123」和「A 的探测碰巧打中 B 的映射」是同一件事，一中两个方向同时放行。暴力扫 64512 个端口约 100 秒、像扫描、撑爆 NAT 表 → 让 B 帮忙：B 开 256 个 socket 朝 A 发包开出 256 个映射，A 随机探测 N 个。单个探测命中约 1/250（不是 1/10），N≈180 过半、N=1024 约 98%（06 第 3.2 节实测吻合），1.6 秒发完。两边各出一份力、在中间相遇 → 生日攻击。**永远是概率，所以必须有预算（发完就停）和中继兜底** |
| 家里有公网 IP + 端口转发，还要打洞吗（2026-11-09） | 不用。放行：端口转发 = 手工写进 NAT 表的**永久行**，且不核对来源（对这个端口就是 full cone）；公司那侧是发起方，自家 NAT 由出包自动建状态，回包放行——**只要有一端可达就不用打洞**，整个 Web 就是这么工作的。寻址：镜子和传话没有消失，而是退化——家宽公网 IP 会变（重拨换 IP），DDNS = 路由器自己看 WAN 口 / 问「我的 IP」（镜子）+ 写进 DNS（慢速单向的传话）。坑：WAN 口是 100.64.x.x 就是 CGNAT，转发无效；国内家宽常封入站 80/443。安全：端口转发对全网开放，几分钟就会被扫描，必须靠应用层认证；打洞的洞（APDF）只放行特定对端，自带一层隐蔽 |
| 打洞为什么两边都要发包（2026-11-09） | 前提：B 已做过 STUN + 信令，A 知道 B 的正确地址（寻址已解决）。B 若不往 A 发包，B 的 NAT 上 6000 那行只为 STUN 开，A 的包被丢——卡在**放行**。**自己发的包是给自己开门的，不是为了送到对方**；真正穿过去的是对方的包。B 是 full cone 时不发也行（等于端口转发）。这也是低 TTL 预热成立的原因：包到不了对方，但门已经开了 |
| 低 TTL 的包到不了对方，为什么还要发（2026-11-09） | 两半：**做到的**——出自家 NAT 时写下「允许对方回来」那一行，这就是它全部的工作；**故意没做到的**——不落到对方 NAT 上。对方 NAT 若不设防（Linux 路由器没有 INPUT 丢弃），抵达的包会在那里留下一条 conntrack 记录，对方随后出包时映射和它冲突、被换端口，于是寻址又错了（docs/06 第 2 节，port ↔ port 也会僵死）。所以 TTL 刚好够出自家所有 NAT、又到不了对方：只开自己的门，不在别人家留脚印 |
| hy2 转发 TCP 用流、转发 UDP 用 DATAGRAM，为什么（2026-11-09） | 看**里层自己管不管可靠**。TCP：hy2 在本地把 TCP 拆开（终结），只取字节流塞进 QUIC 流，对端再新建 TCP 连目标，跨网那段只剩 QUIC 一层可靠。UDP：里面装的是游戏、语音，或者 WireGuard、QUIC 这类自带重传的协议，它们要么自己重传，要么宁可丢也不要迟到的数据。塞进可靠流会出两个问题：① **队头阻塞**——丢一个包，后面已经到的包全得排队等它补上，表现为卡一下再一股脑涌出；可靠流不会因丢包中断，反而是死等不放弃，而迟到的语音帧、旧的游戏状态到了也没用；② 里层若自带重传，就成了两层可靠 → meltdown（同 TCP over TCP）。所以 UDP 原样装进 DATAGRAM，丢不丢、补不补由里层决定。一句话：**能拆开的就拆开、由外层负责可靠；拆不开的就原样装箱、由里层负责** |
| 两个 Brutal 共用一条瓶颈、各设容量的 80%，会怎样（2026-11-09） | 加起来超过容量 → 瓶颈队列塞满 → 丢包。普通拥塞控制看到丢包会让步，Brutal 反而**多发去补**，于是更堵、更丢；两边都不让，谁也没赢：各自拿到的大约只有一半，还要额外搭上补发的浪费，队列一直满着，延迟高、丢包高。同一条路上的 Cubic / BBR 用户被挤到几乎没有（它们会让）。本质是囚徒困境：一个人不让步占便宜，人人都不让就一起变差。单人版已在 docs/09 第 6 节实测过：速率设得比真实带宽高，延迟涨到 1 秒。所以 Brutal 只适合**瓶颈只归你一个人用、且速率设得不超过实测带宽**的场合 |
| sym ↔ sym 为什么没希望（2026-11-09） | 生日攻击成立的前提是有一端（EIM）是**固定靶子**：锥形端不管探测哪个端口，出口都是同一个，对称端 256 个 socket 瞄它就行。两端都对称时，A 每换一个目的端口就开一个新的随机出口端口，靶子在动；而且命中要求**成对**：A 从 a 发往 B:b，同时 B 恰好有一个专为 A:a 开的映射 b，两边的端口互相依赖，等于两边同时猜中对方为自己准备的那一个，而不是打中 256 个里任意一个。实验室 0/10。用词注意：对称说的是**映射**（换目的地就换端口），不是**过滤**严格；「严格」是 APDF 的事。现实出路：端口可预测的对称 NAT（递增）可以猜、IPv6 没有 NAT、UPnP / PCP 让路由器主动开门，其余只能走中继（UU 远程 12 秒打不通就回退 TURN） |
