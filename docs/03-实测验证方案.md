## 03 · 怎样亲手验证 UU 远程的行为

目标：把 01 里标 **[推断]** 的内容逐条变成 **[确认]**。抓包结果放到 `../captures/`。
原则：只分析自己设备上的流量，不破解、不改二进制、不滥用网易的中继节点。

### 1. 抓包工具

| 平台 | 工具 | 备注 |
|---|---|---|
| Windows | Wireshark + Npcap；TCPView 看 `GameViewerServer.exe` 开了哪些端口 | 首选 |
| Android | PCAPdroid（免 root，VPN 方式，可导出 pcap）；或者在 APatch root 后用 `tcpdump` | PCAPdroid 走 VPN 会影响 P2P 判断，最好用 tcpdump |
| Linux | `tcpdump -i any -w uu.pcap udp` 抓路由器镜像或在主路由上抓 | — |

### 2. 看什么

**Wireshark 过滤器**：`stun || dtls || rtp || rtcp || classicstun`

| 观察到 | 说明 |
|---|---|
| STUN Binding Request，带 `USERNAME = xxxx:yyyy`、`ICE-CONTROLLING`、`PRIORITY` 属性 | 标准 ICE 连通性检查 ✅ 坐实 WebRTC/ICE |
| 紧接着 DTLS ClientHello | WebRTC 加密握手 |
| 之后大量 UDP 包，Wireshark "Decode As → RTP" 能解析 | SRTP 媒体；否则是自研协议 |
| TURN `Allocate` / `ChannelData`（头两字节 0x40~0x7F） | 走的是中继 |

**判断 P2P 还是中继**：Statistics → Conversations → UDP，按字节数排序。流量最大的那条：
- 对方 IP = 被控端家里的公网 IP（用 `lab/stunprobe` 在被控端查）→ **P2P 直连**
- 对方 IP 属于网易或云厂商机房（查 ip138 / `whois`）→ **中继**

### 3. 实验矩阵

| # | 场景 | 预期 | 记录 |
|---|---|---|---|
| 1 | 两端同一局域网 | host 候选直连，延迟 <5ms | |
| 2 | 控制端用手机 4G/5G 热点 | 移动网络常为对称 NAT，看是否仍 P2P、有没有端口喷洒（大量发往不同端口的 STUN） | |
| 3 | 两端都在移动数据网络 | 可能走中继，记下中继 IP 与延迟 | |
| 4 | 防火墙禁出站 UDP（仅放行 53） | 看是否回退 TCP/TLS 443（TURN over TCP）以及画面质量 | |
| 5 | 被控端开启 IPv6 | 看候选里是否有 IPv6、是否优先 | |
| 6 | 连接中途切换 Wi-Fi→4G | 看 ICE restart 用时 | |
| 7 | 用 `tc qdisc ... netem loss 3%` 人为丢包 | 看码率/分辨率怎样自适应、画面是否还流畅（FEC 的效果） | |

### 4. 静态线索（只看字符串，不改程序）

在安装目录对 `GameViewer*.exe` 和 DLL 做 `strings`，搜：
`webrtc`、`libjuice`、`usrsctp`、`dtls`、`srtp`、`nvEncodeAPI`、`amf`、`mfx`/`vpl`、`openh264`、`dav1d`、`av1`、`hevc`、`opus`
能判断用了哪套 WebRTC 实现、哪种编码器。也可以看 DLL 清单里有没有 `webrtc.dll` 一类文件。

信令是 HTTPS，可以试着用已有的 mitmweb 看 API 结构；如果客户端做了证书锁定就抓不到，那就算了，不要绕过锁定。
