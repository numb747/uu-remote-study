# 13 · p2pcp 与 sendme（iroh）对比实测

2026-11-21。动机：打算把 p2pcp 做成「先体检、再直传」的自用工具（自己和熟人用），先看看现成的同类工具做到了什么程度，决定继续自研还是改用 iroh。

## 1. 对手：sendme 0.37.1（iroh 1.x）

sendme 是 n0 官方基于 iroh 的传文件工具，思路和 p2pcp 几乎相同：QUIC，先打洞，打不通走中继，校验 + 续传。差别：

| | p2pcp | sendme / iroh |
|---|---|---|
| 会合 | 99-server UDP 7001，房间号 = HMAC(房间名) | 中继兼任会合：TCP 443 上 HTTPS → WebSocket；地址也发布到 `dns.iroh.link`（pkarr） |
| 查公网映射 | 会合服务器回执 | QAD（QUIC 地址发现，中继的 UDP 7842），同时测「映射随目的地变不变」 |
| 打洞 | 先打洞，通了再握手 QUIC；两轮不通才走中继 | 先经中继握手、立刻能传，同时在 QUIC 里打洞（QNT 扩展），通了把直连路径设为主、中继降为备用 |
| 中继 | 自建 UDP 3478（3M 出口） | n0 公共中继：美西、美东、欧洲、新加坡，国内没有；可自建 `iroh-relay` |
| 认证 | 共享房间名 + 通道绑定 | 256 位节点公钥，ticket 里带公钥 + 中继 URL + 直连地址 |

PC 端 sendme 来自 pacman `extra/sendme`；手机端用官方 GitHub Release 的 `linux-aarch64`（静态链接，sha256 与 release digest 一致），adb 推到 `/data/local/tmp` 直接能跑，没有 `/etc/resolv.conf` 也能解析中继域名。

## 2. 方法

`lab/real/vs-sendme.sh`（汇总 `vs-sendme-parse.py`）。PC 家宽（开着 sing-box TUN，两个工具都绑 wlan0 地址），手机电信 5G。两端各一个 50MB 随机文件，p2pcp 与 sendme 交替跑，每个方向 3 轮，都用默认参数。

计时：先让一端就绪（p2pcp 是接收端先挂着，sendme 是发送端先拿到 ticket），从「后上线的一端」启动命令算到它退出。
「建连」是能开始传数据的时刻：p2pcp 取发送端日志第一行到「连上」（日志里的「用时」只是会合 + 打洞，不含之后的 QUIC 握手和认证，而「连上」那行是握手完才打的，所以不能直接用）；sendme 取接收端日志里的 `conn::connected`（通常经中继），「到直连」取第一个 `path::selected network_path=Ip(...)`。

## 3. 结果

| 工具 | 方向 | 轮 | 总时长 | 建连 | 到直连 | 最终路径 | 吞吐 Mbps |
|---|---|---|---|---|---|---|---|
| p2pcp | 手机→PC | 1 / 2 / 3 | 14.3 / 12.3 / 14.6s | 168 / 173 / 176ms | 同建连 | 直连 | 30 / 35 / 30 |
| sendme | 手机→PC | 1 / 2 / 3 | 14.2 / 13.9 / 15.1s | 1362 / 865 / 1416ms | 1909 / 1466 / 2416ms | 直连 | 33 / 32 / 31 |
| p2pcp | PC→手机 | 1 / 2 / 3 | 4.1 / 5.2 / 4.0s | 181 / 183 / 223ms | 同建连 | 直连 | 114 / 86 / 116 |
| sendme | PC→手机 | 1 / 2 / 3 | 6.2 / 9.8 / 7.4s | 1360 / 1250 / 2128ms | 2034 / 1800 / 2864ms | 直连 | 87 / 49 / 80 |

12 轮 sha256 全对，两边都是 6/6 打洞成功。

拆 PC→手机 的吞吐差距，p2pcp 改单连接补测（各 2 轮）：

| p2pcp 参数 | 吞吐 Mbps | 发送端统计 |
|---|---|---|
| 默认（2 条 + BBR） | 114 / 86 / 116 | 丢失 0 |
| 1 条 + BBR | 102 / **13** | 第 2 轮全程 10~18 Mbps，丢失 0，SRTT 39ms |
| 1 条 + Cubic | 79 / 82 | 丢失 0.40% / 0.08% |

## 4. 读数

- **打洞成功率分不出高下**：这一对是 PC（EIM，端口保持）↔ 手机 CGNAT，属于容易打的组合，谁来都通。难的组合（对称 NAT）这次没测到。
- **建连：p2pcp 约 180ms，sendme 约 1.3s 才能传、约 2s 切到直连。** sendme 后上线的一端要先对三个中继做 QAD（约 0.5s）、再经 TLS + WebSocket 连上 home relay（PC 上这条 TCP 被 TUN 接走、经代理出去），然后在美国 / 欧洲中继上握手（RTT 150~300ms），最后打洞（0.4~0.7s）。慢的根源是**中继离得远**，不是打洞本身。p2pcp 的会合服务器在国内，RTT 约 30ms，而且只用 UDP。
- **但 sendme 的设计更稳**：它先经中继就能传，打洞是在后台把路径升级成直连；p2pcp 要等打洞结果，打不通时两轮之后才走中继（实验室 sym ↔ sym 要 8 秒）。
- **手机→PC 两者一样**：瓶颈是 5G 上行（30~35 Mbps）。
- **PC→手机 p2pcp 默认快约 40%，主要来自 2 条连接**：单连接时 p2pcp 也是 80~100，和 sendme 的 80 差不多。手机下行很不稳，单连接 BBR 有一轮在无丢包的情况下全程只有 13 Mbps，样本太少，不足以比较两种拥塞控制的优劣。

## 5. 自建 iroh-relay 之后（同日）

99-server 上跑官方 `iroh-relay` 1.5.0：

- 证书用 Let's Encrypt 的 **IP 证书**（2026-01 起 GA，只有 6 天的 shortlived profile；Ubuntu 26.04 自带的 certbot 4.0 太老，用 snap 版 5.10，`--standalone --http-01-address <内网地址> --ip-address <公网 IP> --preferred-profile shortlived`）。iroh 客户端校验中继证书，QAD 也走同一张证书，没有受信任的证书就查不到公网地址、打不了洞。
- 中继 HTTPS 443；QAD 固定在 UDP 7842，sendme 的命令行改不了，安全组要放行。7842 没放行时 `net_report` 报 `udp_v4: false`，全程走中继（实测 1MB 用了 3 秒），也不会自己报错。
- 访问控制用 `access.shared_token`，客户端把 token 放在 URL 里：`--relay 'https://<IP>/?token=…'`。不带 token 时发送端连不上中继，ticket 都打不出来。
- systemd 临时单元，`DynamicUser` + 只给 `CAP_NET_BIND_SERVICE`，证书和配置用 `LoadCredential` 传进去。

三方交替各 3 轮（20MB，`OWN=… vs-sendme.sh run3 3`），18 轮 sha256 全对，全部直连：

| 工具 | 方向 | 总时长 | 建连 | 到直连 | 吞吐 Mbps |
|---|---|---|---|---|---|
| p2pcp | 手机→PC | 5.1s | 237ms | 237ms | 40 |
| sendme（n0 中继） | 手机→PC | 7.5s | 1053ms | 1872ms | 27 |
| sendme（自建中继） | 手机→PC | 4.8s | 200ms | 452ms | 36 |
| p2pcp | PC→手机 | 2.3s | 217ms | 217ms | 88 |
| sendme（n0 中继） | PC→手机 | 5.7s | 1594ms | 2835ms | 45 |
| sendme（自建中继） | PC→手机 | 2.6s | 247ms | 536ms | 71 |

（中位数）

- **中继搬到国内后，sendme 的建连从 1~1.6s 降到 200~250ms，到直连从 2~3s 降到约 0.5s**，和 p2pcp 基本持平。QAD 延迟从 140~230ms（欧美）降到 24ms。之前慢，全是因为中继离得远。
- 两者的时间结构不一样：sendme 约 200ms 就能经中继开始传，约 250ms 后切到直连；p2pcp 约 200ms 直接就是直连，但这期间什么都传不了。
- p2pcp 有 1 轮（手机→PC 第 3 轮）建连花了 4.5s：打洞本身只用了 118ms，**之后的 QUIC 握手 + 认证花了约 4.4s**，接近 quic-go 握手包连续重传几次的累计时长（0.3 + 0.6 + 1.2 + 2.4s）。疑似握手包在对方还在打洞循环里时被当成非打洞包扔了，待查。日志里的「用时」只算会合 + 打洞，所以看不出这段等待。
