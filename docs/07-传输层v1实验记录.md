# 07 · 传输层 v1 实验记录（M4）

## 1. 做了什么

| 组件 | 位置 | 说明 |
|---|---|---|
| 假编码器 | `lab/fakeenc` | 60fps、默认 20Mbps；每 120 帧（2 秒）一个关键帧，大小是普通帧的 8 倍（约 315KB，263 个包）；普通帧约 39KB ±20% |
| 自研传输 v1 | `lab/transport` | 分片 ≤1200 字节 + 按传输序号 NACK 重传 + 截止时间丢弃；明文；**没有** FEC、Pacer、拥塞控制。包格式见 `packet.go` 头部注释 |
| 测试工具 | `lab/xfer` | 三种传输共用同一个假编码器和同一套接收端统计口径 |
| 实验室接入 | `lab/netns/lab.sh xfer`、`xfer-bench.sh` | 接收端在 inet（相当于公网服务器），发送端在 peerA 的 NAT 后面；弱网加在 A 的接入链路上、双向生效 |

三种传输：
- **own**：自研 v1。
- **quic**：quic-go v0.63，**每帧一个单向流**，到截止时间还没送达就 `CancelWrite`。重传、拥塞控制（Cubic）、发包节奏全交给 QUIC。这是 Media-over-QUIC 一类方案的典型用法，比"DATAGRAM 上再自己做重传"更能代表 QUIC 本身的水平。
- **tcp**：一条连接按顺序发所有帧，用来看队头阻塞。

指标口径（接收端统计）：
- 帧延迟 = 收齐时刻 − 发送端编码完成时刻（netns 里两端是同一台机器，时钟天然同步）。截止时间 100ms。
- **可播放**按解码依赖算：P 帧的有效显示时刻 = max(自己收齐, 上一帧有效显示时刻)，有效延迟 ≤ 100ms 才算可播放；一帧彻底没收到就断链，冻结到下一个关键帧。v1 没有"丢帧后请求关键帧"，所以一次断链最多冻结 2 秒。

## 3. 读数

1. **基于丢包的拥塞控制不适合远控。** 1% 随机丢包、40ms RTT 下，按 Mathis 公式，Reno/Cubic 的吞吐上限约为 MSS/RTT × 1.22/√p ≈ 3.5Mbps（Cubic 稍好，实测 QUIC ≈ 8.6Mbps），远低于 20Mbps。Wi-Fi、4G 上的随机丢包并不代表拥塞，但 Cubic 会把它当拥塞来降速。这验证了 05 章"看延迟而不是看丢包"的判断。
2. **TCP 的队头阻塞会让延迟无限累积**：带宽不够时，帧在发送缓冲里越排越长，延迟涨到几十秒。即使带宽够（3Mbps），关键帧 p50 也要 142ms。这就是基于 TCP 的远控"拖泥带水"的原因（01 章 3.3）。
3. **QUIC 的"每帧一流"有个隐患**：quic-go 在流之间轮流发送，带宽紧张时 60 个帧同时各前进一点，谁都赶不上截止时间。媒体传输需要**旧帧优先**（或者按截止时间优先）的调度。
4. **自研 v1 在 1% 丢包下表现不错（可播放 96%），3% 时就垮了**，问题集中在两点：
   - **截止时间内只够重传一次**：100ms 截止、40ms RTT，重传包再丢一次或者 NACK 本身丢了，这帧就没救了。3% 丢包下约 5% 的帧因此丢失。→ 需要 **FEC**，用冗余代替等重传。
   - **关键帧是最大的弱点**：263 个包本身就要 73ms 才能发完（50Mbps），再加一次重传（+40ms）就超过 100ms 截止时间；收不齐就冻结 2 秒。→ 需要 **关键帧加大 FEC 冗余、丢帧后请求关键帧（PLI）、或者用 intra-refresh 把关键帧摊开**。
5. **没有拥塞控制是 v1 占的便宜**：随机丢包时它照发不误所以占优，可一旦链路真的比码率窄，它会把队列塞满（SRTT 689ms）。QUIC 不会超发，但编码器不降码率，结果一样。→ **基于延迟的带宽估计，并把结果反馈给编码器（`fakeenc.SetBitrate`）**，是 M5 的核心。
6. 抖动 ±5ms 会让 netem 打乱包的顺序，v1 一看到序号空洞就立即 NACK，会把乱序误判成丢包。可播放从 96% 掉到 78%，说明还需要一个小的乱序容忍窗口。

## 4. 实现中踩到的坑

- **防重复重传误伤首个 NACK**：最初"一个 RTT 内只重传一次"的判断用的是"上次发送时刻"，首发也算进去了。首个 NACK 到达时离首发通常不到一个 RTT，于是被当成重复扔掉，3% 丢包下按时率只有 51%。改成只看上次**重传**时刻后，回到 92.5%。
- **开头丢的包永远不会被 NACK**：接收端最初从收到的第一个包开始计序号。改成从 seq 0 开始，开头丢的包也能被发现。
- **实验室的 ARP 队列会吃掉关键帧**：新建的网络 ARP 还没解析，关键帧一次涌出 263 个包，超出 ARP 等待队列的部分被直接丢掉。实验室现在会先 ping 一次。真实公网上邻居早已解析好，没有这个问题。

## 5. 下一步（M5）

按收益排序：
1. **基于延迟的带宽估计（trendline）+ 编码器码率闭环**：解决链路比码率窄时塞满队列的问题。传输序号已经为此设计好，每个 seq 只发一次，到达时间没有歧义。
2. **FEC**（Reed-Solomon，按帧分组，关键帧加大冗余）：解决 3% 丢包下"只够重传一次"的问题。
3. **Pacer**：把关键帧的 263 个包均匀铺开发送，避免瞬间塞满路由器队列造成自己丢包。
4. **PLI（丢帧请求关键帧）**：冻结从最长 2 秒缩短到约 1 个 RTT。
5. **NACK 乱序容忍窗口**（几毫秒），减少抖动下的无效重传。
