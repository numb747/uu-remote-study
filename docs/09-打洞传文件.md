# 09 · 打洞传文件：手机 5G → PC（p2pcp）

2026-10-16。把前面的打洞和传输拼成一个能用的东西：两端各执行一条命令，经会合服务器交换地址，打洞，然后在打通的同一个 UDP socket 上跑 QUIC，可靠地传文件。

```bash
p2pcp recv -bind 192.168.1.95 -room demo -o ~/Downloads      # PC（开着 TUN 时绑物理网卡）
p2pcp send -room demo -conns 4 /data/local/tmp/xxx.mp4        # 手机（adb shell）
```

## 1. 实现要点（`lab/p2pcp`）

- **会合**：直接用 `punch server`（REG/PEER 协议；原来是 UDP 7000，第 7 节起改为 7001）。对端候选 = 服务器看到的公网映射 + 对方自报的内网地址，同时向所有候选打洞，哪个先回应就用哪个。同一个局域网时内网地址 RTT 最小、最先回来，这就是 ICE 的 host 候选。
- **打洞**：每 20ms 一个探测 + 触发检查（docs/08 第 3.1 节的结论）。实测 64~264ms 打通。
- **QUIC 接管同一个 socket**：`quic.Transport{Conn: 打通的 UDPConn}`，接收端 Listen、发送端 Dial。NAT 映射就是打洞时开出来的那个。打洞消息以 `/`（0x2f；最初是 0x01）开头：quic-go 只把首字节最高两位为 0 的包交给 `ReadNonQUICPacket`，所以 QUIC 接管之后，对方迟到的探测仍能被识别并回应。
- **保活**：`KeepAlivePeriod` 10 秒。docs/08 测出两端映射寿命最短 60 秒。
- **多连接**：`-conns N` 打 N 个洞、开 N 条 QUIC 连接，各传文件的一段，接收端按偏移写到同一个文件。第 0 条连接的头里带着总连接数，接收端读到后再去接其余几条。
- **校验**：实验阶段两端各算一次 sha256，结果都一致；封装成软件后去掉了（QUIC 本身保证可靠交付，300MB 在手机上算一遍要一两秒）。
- **云服务器当接收端**：会合服务器跑在同一台机器上时，它看到的来源是 127.0.0.1，所以加了 `-public <公网 IP>`，把公网地址也报成候选。

测试文件是 ffmpeg 生成的 1080p60 测试图案视频（`testsrc2` 加噪点，40Mbps，60 秒，296MB），加了噪点后压缩不了，传输上等同于真实录像。

## 2. 结果

| 路径 | 连接数 | 用时 | 平均 | 发送端统计 |
|---|---|---|---|---|
| 手机 → PC | 1 | 2 分 12 秒 | **17.9Mbps** | 判定丢失 0.04%，SRTT 44ms |
| 手机 → PC | 4 | 52.5 秒 | **45.1Mbps** | 每条的 SRTT 42~187ms |
| 手机 → PC | 8 | 50.2 秒 | **47.2Mbps** | 每条的 SRTT 49~236ms |
| 手机 → 服务器（对照） | 4 | 49.1 秒 | **48.3Mbps** | 服务器入方向不限速 |

每次 sha256 都一致。

### 读数

1. **瓶颈是手机的 5G 上行，约 48Mbps。** 直接传给服务器也只有 48Mbps，所以 PC 的家宽下行和"电信 → 联通"跨网都不是瓶颈。4 条连接的直连已经跑到上限的 95%。
2. **单条 QUIC 只跑出 40%，问题在 Cubic。** 判定丢失只有 0.04%，按 Mathis 公式，1.22 × MSS / (RTT × √p) ≈ 13Mbps，和实测的 18Mbps 同一量级。docs/08 第 5 节已经看到这条路上的"丢包"基本是乱序，所以 Cubic 是在因为乱序而降速。多条连接各自减半、互不影响，加起来就把链路填满了。这正是 BitTorrent、多线程下载器用多连接的原因。
3. **多连接是有代价的：缓冲区被填满。** 4 条、8 条连接时 SRTT 从 30ms 涨到 190~240ms，上行缓冲被塞满了。如果这时候还在用这台手机远控或者打游戏，延迟会被拖垮。基于丢包的拥塞控制靠把队列塞满来"探测"带宽，所以填满带宽和保持低延迟两件事不可兼得。

## 3. 还能更快吗

| 方向 | 能提升多少 | 说明 |
|---|---|---|
| **单连接跑满**（延迟/带宽模型的拥塞控制，BBR 或 M5 的延迟 BWE） | 1 条连接也能跑到约 45Mbps，并且**不塞满缓冲区** | quic-go 没有 BBR。要么自己的传输做大文件模式（NACK 重传，按估计带宽发包），要么换实现。这和远控视频要的是同一套能力 |
| **同一个局域网**（手机连家里 Wi-Fi） | 从 48Mbps 到几百 Mbps | p2pcp 已经会报内网候选，在同一个局域网里会自动走内网，不用改代码。AirDrop、LocalSend 快就快在这里 |
| **多路径**（5G 和 Wi-Fi 同时用） | 两条之和 | MPTCP/MPQUIC 的思路。在手机上要能把 socket 绑到指定网络，adb shell 下做不到，要做成 App |
| 换时段、换位置 | 5G 上行随信号和小区负载变化很大 | 不是工程手段 |
| 压缩 | 对视频无效 | 视频已经压缩过了 |

**结论**：在"手机走 5G"这个前提下，物理上限就是 5G 上行，目前已经跑到 95%；剩下值得做的，是用更好的拥塞控制让**一条**连接就跑满，而且不拖高延迟。真正的数量级提升，来自让传输走更宽的路，也就是局域网或多路径。

## 4. 遗留问题

- **偶发打洞失败**：第一次传输（房间 t1）双方都拿到了候选，但 30 秒没打通；之后 7 个会话（共 20 多个洞）全部成功。docs/08 第一批 setup 测试里也有 4 次类似的失败，当时归因于脚本时序，现在看未必。`P2PCP_DEBUG=1` 可以打印每个收到的包，下次出现时能看出是哪个方向不通。

## 5. 封装成软件：「P2P 直传」（2026-10-16）

把 p2pcp 包成手机 App + 电脑端常驻服务，两个方向都能点着用：

| | 手机（`apps/android`） | 电脑（`apps/pc`） |
|---|---|---|
| 发 | App 里点「选择文件，发到电脑」，或在相册 / 文件管理器里「分享 → 直传到电脑」 | 启动器「发送到手机（P2P 直传）」弹文件框；Dolphin 右键「P2P 直传到手机」 |
| 收 | App 开着时常驻接收，存到「下载/P2P直传」 | systemd 用户服务 `p2p-direct` 常驻接收，存到 `~/Downloads/P2P直传`，桌面通知显示进度 |
| 构建 / 安装 | `apps/android/build.sh install` | `apps/pc/install.sh`（`uninstall` 卸载） |

- **房间**：`~/.config/p2pcp/room` 是 24 位十六进制的随机密钥。电脑收件用 `<密钥>.pc`，手机收件用 `<密钥>.phone`，两个方向分开，常驻的两端不会抢同一个 id。手机 App 构建时把密钥写进 assets。这个密钥就是唯一的"认证"：知道它的人可以往你的收件目录里发文件。TLS 不校验证书，会合服务器理论上能做中间人。自用够了，给别人用之前要补配对和证书固定。
- **会合服务器常驻**：99-server 上的 `uu-rendezvous.service`（就是 punch server，加了 UNREG：拿到对方地址就注销，免得常驻端 30 秒内被推送上一次的旧地址）。`DynamicUser`、内存上限 64M。
- **手机 App 不用 Gradle**：`aapt2` + `javac` + `d8` + `zipalign` + `apksigner`，`android.jar` 从 Google 仓库下载到 `~/.cache`。界面是纯 Java、没有 AndroidX，代码在一个文件里。传输核心就是 Go 编译的 p2pcp，**伪装成 `lib/arm64-v8a/libp2pcp.so`**：Android 10 起 App 不能执行自己数据目录里的文件，但安装器解压到 nativeLibraryDir 的"库"可以执行（`extractNativeLibs=true`）。界面解析它 stdout 上的 `@STATE/@PROGRESS/@DONE/@ERROR` 行。
- **Android 11+ 的坑**：App 里的 Go 程序读不到网卡列表（netlink 被限制），所以由 Java 的 `NetworkInterface` 取内网 IP，通过 `-lan` 传给它，用于同一局域网时走内网候选。
- **限制**：手机只有 App 在前台时才收得到（熄屏或切后台后进程会被冻结，所以 App 保持亮屏）；要做到后台常驻，得改成前台服务。电脑换网络后，常驻服务绑定的还是旧网卡地址，要重启服务（`systemctl --user restart p2p-direct`）。
- **实测**：电脑 → 手机 App 20MB 用时 4.8 秒（33Mbps）；手机 → 电脑服务 2MB 0.8 秒。小文件慢的问题见下一条。
- **小文件慢**：2MB 单连接有时只有 3~4Mbps：连接刚开始时 Cubic 碰到几个丢包（3%，大文件稳态时只有 0.04%），cwnd 一直起不来。大文件靠 4 条连接掩盖了这个问题，根治要换拥塞控制（第 3 节）。

## 6. Hysteria 2 的拥塞控制对比 + 偶发打洞失败的根因（2026-10-16 傍晚）

**拥塞控制**：换成 Hysteria 的 quic-go 分支（`github.com/apernet/quic-go`，可替换拥塞控制），把它的 BBR 和 Brutal 移植到 `lab/third_party/hyscc`（MIT 许可证），p2pcp 用 `-cc cubic|bbr|brutal:45M` 选择。手机 → PC，150MB，**单连接**，同一时段（此时链路约 35Mbps，比上午低）：

| 拥塞控制 | 平均 | 发送端 SRTT | 发包数（理论最少 11.45 万） |
|---|---|---|---|
| cubic | 16.7Mbps | 55ms | 11.45 万 |
| **bbr** | **32.2~34.9Mbps** | 86ms | 11.45 万 |
| brutal:30M（低于容量） | 29.1Mbps | 34ms | 13.1 万 |
| brutal:45M（略高于容量） | 32.1Mbps | **995ms** | 15.6 万（多发 36%） |
| brutal:80M（远高于容量） | 34.2Mbps | **887ms** | 27.0 万（多发 136%） |

- **BBR 单连接就比 Cubic 快一倍**，接近链路容量，延迟只涨到 86ms，也不浪费流量。
- **Brutal 的速度取决于设定值**：低于容量时又稳又快；一旦设高了，速度不会再涨（链路就这么宽），但队列会塞满到 1 秒，丢的包它还会加倍补发，白白浪费流量。hy2 快，是因为用户手动填了带宽、而且通常填得合适；它不适合带宽会变的 5G。
- 结论：要快且稳，用 **BBR**。4 连接 BBR 的对比还没测（被打洞失败打断），默认值暂时仍是 4 条 Cubic（第 7 节已改为 BBR、2 条）。

**偶发打洞失败的根因**：失败的连接里，手机分到的公网端口全是 1024 以下的低端口（1、2、11、14、17、32、35、49、58、68、106、136……），成功的全在 18xxx。电信 CGNAT 的 18xxx 端口块用满后，会分 1~437 的低端口段；这些端口上**外面的包进不来**，连会合服务器的回包都收不到（大概率是运营商或云厂商拦截低端口）。修复分两层：

1. 会合服务器对每个 REG 回执 `YOU <公网地址>`。客户端发现自己被映射到低端口，或者 2 秒内没收到回执，就扔掉这个 socket，换新的。
2. 单轮打洞超时从 15 秒改成 4 秒，失败就换一对新端口重来，最多 6 轮（兜住 conntrack 冲突之类的其他原因）。

修复后 15 次 × 4 条连接全部成功：期间 5 次被映射到低端口、6 次打洞超时，都在下一两轮恢复。测试时短时间内开了大量 socket，所以低端口出现得特别多；平时用的时候少见。

## 7. 会合端口 7000 被拦、BBR 设为默认、IPv6 候选（2026-10-17）

### 7.1 手机换了 CGNAT 后全部打不通：根因是会合服务器用了 UDP 7000

**现象**：第二天早上，手机 5G 的内网地址从 `100.106.x.x` 变成 `10.73.243.91`，公网出口变成 `27.128.49.243`，说明换到了另一台电信 CGNAT。p2pcp 每一轮都打洞超时，6 轮全部失败。两边都拿到了对方的候选，但一个探测包都没收到。

**排查**（排除法，每一步只改一个变量）：

| 试了什么 | 结果 | 说明 |
|---|---|---|
| natprobe 测新 NAT | EIM + 端口块随机分配（24684~24770） | NAT 类型跟昨天一样，不是对称型 |
| 手工打洞工具 natprobe peer（地址由脚本交换） | 3/3 成功，35~49ms | 这两个网络之间本身能打通 |
| natprobe peer 改成先问我们服务器的 3478 | 3/3 成功 | 跟哪台 STUN 服务器通过信都没关系 |
| p2pcp 探测包首字节 `\x01` → `/` → `H`，补到 48 字节 | 仍然 0 个包 | 跟包内容和包大小都没关系 |
| p2pcp 只打公网候选 | 仍然失败 | 跟内网候选无关 |
| 服务器当接收端，在服务器网卡上抓包 | 只抓到手机发往 7000 的 6 个 REG，打洞包一个都没到 | ~~手机这个 socket 发往别处的包在运营商那里就没了~~ **这条推论不成立**：接收端用的是随机端口，阿里云安全组只放行了 3478-3479、7000-7001，包本来就会被安全组挡掉（第 8 节） |
| **会合服务器换到 UDP 7001**，其余不变 | **第一轮 78ms 打通** | 问题就出在会合端口 |

**结论**：在这台电信 CGNAT 后面，一个 UDP socket 只要先和 7000 端口通过信，之后往别处发包用的就**不是**会合服务器看到的那个公网映射。第 8 节用 `p2pcp check` 实测到：先问 7000，映射是 24728；同一个 socket 再问 7001，映射变成 24828。先问 7001 的 socket 则不会这样，再问 7000 时映射不变。

于是会合服务器转告对方的地址，和我方打洞包实际的出口对不上：对方往 24728 打洞，我方的包从 24828 出去，两个方向的过滤都通不过。换成 3478、7001 都正常，昨天那台 CGNAT 上 7000 也正常；可能是运营商对 UDP 7000 做了特殊处理，单独为它分配映射。p2pcp 和 natprobe 的区别正好在这里：natprobe 会合用的是 3478。

**修复**：
- 99-server 上加了 `uu-rendezvous-7001.service`，原来的 7000 保留。
- p2pcp、电脑端 `p2p-direct`、App 的默认会合地址都改成 `:7001`。

教训：会合、STUN 这类服务用 3478 这类"正经"端口更稳；遇到"两边地址都对、就是一个包都不过"，可以先换一下会合端口试试。

### 7.2 BBR 设为默认：5G 上行 1~2 条就跑满

手机 → PC，150MB，`lab/real/cc-bench.sh`。会合用 7001，5 组都是第一轮就打通：

| 拥塞控制 | 连接数 | 用时 | 平均 | 各连接 SRTT |
|---|---|---|---|---|
| **bbr** | 1 | 22.7s | **52.9 Mbps** | 156ms |
| **bbr** | 2 | 21.2s | **56.5 Mbps** | 153 / 63ms |
| bbr | 4 | 22.4s | 53.5 Mbps | 153 / 112 / 109 / 51ms |
| cubic | 4 | 28.2s | 42.6 Mbps | 153 / 97 / 60 / 53ms |
| cubic | 1 | 44.2s | 27.1 Mbps | 51ms |

同一个局域网（手机连 Wi-Fi，自动走内网候选），150MB：

| 拥塞控制 | 连接数 | 用时 | 平均 |
|---|---|---|---|
| **bbr** | 1 | 4.49s | **267 Mbps** |
| **bbr** | 2 | 4.07s | **295 Mbps** |
| bbr | 4 | 4.34s | 277 Mbps |
| cubic | 4 | 5.54s | 217 Mbps |
| cubic | 1 | 6.15s | 195 Mbps |

- 今天 5G 上行比昨天宽（约 55Mbps，昨天约 48Mbps）。BBR 1 条就跑到 53Mbps，开到 2 条、4 条也不再变快，说明已经到链路上限。
- Cubic 要 4 条才能接近，单条只有一半。原因见第 2 节读数 2：乱序被误判成丢包。
- 局域网里也是同样的规律，BBR 比 Cubic 快 25~50%。
- **新默认值改为 `-cc bbr -conns 2`**：2 条和 1 条的差别在误差范围内，多开一条是为了保险，单条 BBR 有时进 ProbeRTT 会降速。手机 App 和电脑端没有自己传这两个参数，所以直接用上了新默认值。
- 回归测试（20MB）：手机 → PC 36.6Mbps，PC → 手机 **79.2Mbps**。昨天同一个网络、同方向只有 33~37Mbps；今天是周六早上，网络空闲，不全是 BBR 的功劳。

### 7.3 IPv6 候选

IPv6 没有 NAT，只有运营商的状态防火墙。两边同时往外发包就能打开，也就不存在 CGNAT 端口块、低端口、7000 这类问题。实现方式：

- 本机有全局 IPv6（不算链路本地和 ULA）时，每一轮除了 IPv4 socket，再开一个绑在这个地址上的 IPv6 socket。地址的选法：对一个公网 IPv6 地址做 UDP connect 查路由（这一步不发包），拿默认出口上的源地址，这样不会挑到 docker 或虚拟网卡上的地址。默认 IPv6 路由被 TUN 代理接管时，拿到的是 ULA，就不走 IPv6。它的地址 `[v6]:port` 和内网地址一样，作为自报候选，经 IPv4 的会合服务器交换。99-server 没有 IPv6，会合服务器本身不用改，候选串是原样转发的。
- 两个 socket 同时打洞，先通的用，另一个关掉。
- **提名**：两端各自"先收到回应的"未必是同一条路径。可能发送端选了 IPv6，接收端却选了 IPv4 并关掉了 IPv6 socket。所以照 ICE 的做法：
  - 发送端（之后做 QUIC Dial 的一方）用第一个收到回应的路径，并在这条路径上发 3 个 `/PN`。
  - 接收端如果有两个 socket，就等 `/PN` 再定路径。
  - `/PN` 全丢了也有兜底：QUIC 握手包先到了哪个 socket，就说明发送端选的是哪条。只有一个 socket 时，接收端和以前一样，第一个回应就定。
- `-4` 只走 IPv4。`-6` 只走 IPv6，此时 IPv4 socket 只管会合、不应答打洞，否则对方的触发检查会把路径拉回 IPv4。
- Android App 里 Go 读不到网卡列表，由 Java 把全局 IPv6 一起放进 `-lan` 传给它。

**测试**：在 `unshare -rn` 的网络命名空间里，给 lo 挂上 `2001:db8::1`，会合服务器也在命名空间里，测了 4 种组合：两端双栈、发送端 `-6`、接收端 `-4`、发送端 `-4` 且接收端双栈。文件全部一致，两端选的路径也一致。真实网络上测了"手机有 IPv6、PC 没有"，两个方向都正常。

**现状**：
- 手机 5G 有全局 IPv6（`240e:…`）。
- PC 所在的 Wi-Fi 上有 IPv6 路由器，对 `ff02::2` 组播 ping 有应答，但它不下发前缀，PC 只有链路本地地址、没有默认路由。
- 要让 IPv6 路径真正用起来，得在路由器上开 LAN 侧的 IPv6（SLAAC 或 DHCPv6-PD）。开了以后，代码不用再改。

## 8. 健壮性：应对"昨天能用、今天不能用"（2026-10-17）

7000 事件说明，网络环境会在用户不知情的时候变：运营商换了 NAT、某个端口被特殊对待、手机在 Wi-Fi 和 5G 之间来回切、电脑换了网络。这一节把这类变化按"哪一层坏了"分开处理。

### 8.1 哪一层会坏、怎么应对

| 层 | 会坏的情形 | 之前 | 现在 |
|---|---|---|---|
| 会合 | 某个端口被运营商特殊对待（7000 事件） | 只有一个端口，写死在客户端里 | 服务器一个进程同时听 7000 和 7001，**房间共享**；客户端 `-server` 给一串地址，每轮换一个，打通过的记住、下次先用 |
| 会合 | 新旧版本客户端用的端口不同 | 两个独立进程，房间不通，两端永远碰不上 | 房间共享，用哪个端口都能配上对 |
| 会合 | 服务器常驻，房间只增不删 | 内存一直涨，最终撞 64M 上限被杀 | 每分钟清理 5 分钟没动静的成员和空房间 |
| 网络切换 | 电脑换网络 | 常驻服务绑着旧地址，永远等不到人，要手动重启 | `-bind auto`：每轮现取 main 表默认路由那块网卡的地址 |
| 网络切换 | 等待中网络变了、服务器重启了 | 旧 socket 一直等下去 | 保活：会合回执断了 3 个注册周期（daemon 约 17 秒），就换新 socket 重新注册 |
| 网络切换 | 手机 App 的 `-lan`（含 IPv6）在启动时算好，之后过时 | 不更新 | 监听默认网络变化，IPv4 地址集合或"有没有 IPv6"一变就重启 daemon；地址只取**当前默认网络**的（刚切到 Wi-Fi 时 5G 网卡还会挂一阵，它的地址已经用不上） |
| 体验 | 断网时常驻服务反复失败 | 每十几秒弹一次失败通知 | 空等时连不上会合服务器，只更新状态，不弹通知，重试间隔 5 秒到 1 分钟递增；只有真有人来传、却失败了才弹 |
| 诊断 | 打不通时只报"打洞超时" | 不知道是哪一层 | 失败时分层说明（连不上会合服务器 / 能会合但打不通）；新增 `p2pcp check` 体检 |

### 8.2 `p2pcp check`：网络体检

对每个会合地址 P，先用一个新 socket 问 P，再用**同一个 socket** 问其余地址，比较回执和公网映射：

- **P 自己没回执**：这个端口到不了（服务器挂了、端口被拦、安全组没放行）。
- **P 通，但同一个 socket 再问别处，要么没回执、要么映射变了**：P 有毒，经它会合必然打不通。
- **每个地址都这样**：映射随目的地变化（对称型 NAT）。
- **映射端口 < 1024**：CGNAT 的低端口段（第 6 节）。

手机 5G 上的实测，连续两次结果一致：

```
✔ 8.140.18.211:7001  回执 44ms，公网映射 27.128.49.243:24836；同一个 socket 再问 8.140.18.211:7000 ✔
✔ 8.140.18.211:7000  回执 40ms，公网映射 27.128.49.243:24739；同一个 socket 再问 8.140.18.211:7001 ✔ 但映射变成 27.128.49.243:24616
⚠ 8.140.18.211:7000：和它通过信之后，这个 socket 往别处发包用的不是服务器看到的映射，经它会合必然打不通
```

这次才把 7000 事件的机制测清楚（第 7.1 节已更正）。"昨天能用、今天不能用"时，先在两端各跑一次 `p2pcp check`。

### 8.3 验证

- **netns**（`unshare -rn`）：
  - 两端从不同端口注册，能配上对。
  - 第一个会合地址是死的，2 秒后换到第二个打通。
  - daemon 等待中服务器停了 25 秒：17 秒后发现失联，换 socket 重试，不弹通知；服务器恢复后照常收到文件。
- **真实网络**（手机 5G → 电脑常驻服务，20MB）：
  - 默认列表，第一轮就打通，33Mbps。
  - 故意把 7000 排第一：第一轮在 7000 上打洞超时，第二轮换到 7001 打通，多花约 4 秒。
- **App 网络切换**：App 开着时打开手机 Wi-Fi，约 6 秒后重启了接收，自报候选里出现了 Wi-Fi 的内网地址 192.168.1.244。这是第一版（枚举全部网卡）的结果；改成"只取当前默认网络的地址"之后的版本**还没装到手机上验证**。

### 8.4 还没做的

- **中转兜底**：两端都是对称型 NAT，或者 UDP 被整体封掉时，只能经服务器中转。99-server 出方向只有 3Mbps，300MB 要 13 分钟，但总比失败强。
- **断点续传**：传到一半网络断了，现在要从头再传。
- **多一个"正经"端口**：现在列表里只有 7001 是好的（7000 在这台 CGNAT 上有毒）。建议安全组再放行 **UDP 443**：它看起来像 QUIC（HTTP/3），运营商一般不会特殊对待。放行后服务器加听 443，客户端列表加上它即可，不用改代码。
- **单个 send 进程不会记住好端口**：好端口只在进程内记住。如果列表第一个有毒，每次发送都会多花 4 秒；常驻服务不受影响。
